# Retrieval and refresh

Current-state guide — see [review baseline](../architecture.md).

Infrastructure adapters retrieve official structured API/HTTP/HTML data; no production Playwright package. Application orchestrates freshness, bounded refresh and independent persistence. Exact-date verification, provenance, source states and last-known-good remain mandatory. Phase 34B-2 added official POST coalescing accounting for Accesso request nonce (not identical raw bodies); Phase 34C consolidated shared Accesso transport/evidence without changing source-specific mapping. A dormant browser-session seam remains intentionally. Date switches do not retrieve online.

## Dated pricing after the sales window ends (pre-RC.15)

The accesso calendar stops listing the current date once its sales window ends (live-observed 2026-11-27 at 11:12 PM ET for both `SnapWizardDailyTickets` and `FastLaneOnly`), so the next automatic or manual check of that date answers a successful `Unavailable` with no products. `DatedSourceRegistration` normally records every successful completion as the new last-known-good value; for the dated pricing categories whose stored exact-date results are the only record of a date's prices (`HistoricalPricingCapability.StoredObservationsOnly`: dated admission, Fast Lane, haunted/SCarowinds, Bring-A-Friend, BAF Duo, Military/First Responder) `VerifiedDatedPriceRetention` keeps a stored `Verified` payload when the new answer is a payload-less `Unavailable`/`NotPublished`. Only the last-attempt columns are written (`RecordNoOfferAttemptRetainingVerifiedAsync`), so the original verification time and source stay, date freshness (`DateCheckFreshness`, last attempt) is unchanged and no extra request is made. The same applies to a Check Online of a past date (adapter short-circuits to `Unavailable` without a request). A new `Verified` payload always replaces; `Error` keeps the existing failed-attempt path; park hours, shows and catalog sources keep their previous behavior. The stored row is read only for such an answer. Presentation: `AssociateVerificationState.PreviouslyVerified`. Details: [fix record](../pre-rc15-post-closing-pricing-retention.md).

## Weather (Phase 37B backend; activated for the Dashboard in Phase 37C)

Weather is a separate path, not an official Carowinds source and not part of `OfficialDataRefreshCoordinator`, the refresh orchestrator, `SourceResult` states or the scheduled task. `Domain/Weather` holds the models, the two verified park reference points (`CarowindsWeatherLocation.Park`, decision D8) and `WeatherAlertRules`. `Application/Weather` holds the `IWeatherProvider` and `IWeatherCacheStore` ports, `WeatherRefreshPolicy`, the single-flight `WeatherRefreshCoordinator` (refuses every request for an unverified location) and `WeatherSnapshotBuilder`; `Application/Links/WeatherSourceLinkPolicy` allows only the four NWS hosts. `Infrastructure/Weather/Nws` holds its own `NwsHttpTransport` (own `HttpClient`, `api.weather.gov` only, versioned User-Agent with the public repository URL, conditional requests, 2 MB body cap), the parsers and `NwsWeatherProvider`. Request policy, alert handling and failure states: [Phase 37B](../phase37b-weather-retrieval-and-cache.md).

**Activation (Phase 37C).** `App.axaml.cs` registers one `NwsWeatherProvider` (its own `HttpClient`), one `FileWeatherCacheStore`, one `WeatherRefreshCoordinator` at `CarowindsWeatherLocation.Park` and one `IWeatherMonitor` (`Application/Weather/WeatherMonitor`). Only `IWeatherMonitor.Start()`, called once after the main window is assigned, begins retrieval: on the thread pool it reads the cache and publishes it (cached weather works offline), waits `StartupDelay` (10 s), then asks the coordinator for whatever is due (alerts for both points about every 5 minutes, D5; the rest under cache headers, floors and backoff) and sleeps until the next due endpoint, never less than 15 s and never more than 1 minute (each wake rebuilds the snapshot so freshness labels age). Refresh Weather in the Dashboard card's details calls `RefreshNowAsync`, which uses `WeatherRefreshMode.Manual`: endpoints past their minimum interval (`WeatherEndpointPolicy.EarliestAt`: floor and backoff, not cache expiry), through the same single flight; a request while any refresh runs reports "already refreshing". `StopAsync` runs in `AttachShutdownFlush` beside the official-data coordinator, within its 2 s bound. The scheduled-refresh host never resolves or starts the monitor, so nothing is requested while the app is closed. Phase 37F: the Passdown reads `IWeatherMonitor.Current` when it builds a PDF; `OperatingHoursForecastSelector` (pure) selects the hourly periods for the selected date's park hours and never requests anything. Phase 37D: the Calendar reads `IWeatherMonitor.Current` and listens to `Changed` for its selected-date Weather group (`OperatingHoursForecastSelector.OperatingWindow` gives the same park-hours window); date selection and month navigation never request weather. `WeatherSnapshot.AlertCoverage` records which point (NC/SC) returned each active alert. Check Online, the official transport, `OfficialSourceLinkPolicy` and the refresh orchestrator are unchanged; NWS pages open only through `IWeatherLinkLauncher` (`WeatherSourceLinkPolicy`). Details: [Phase 37C](../phase37c-dashboard-weather-integration.md).
