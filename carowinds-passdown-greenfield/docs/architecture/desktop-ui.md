# Desktop UI

Current-state guide — see [review baseline](../architecture.md).

Avalonia MVVM uses a persistent shell and once-created workspaces. `MainViewModel` controls navigation; `AssociateViewModel` owns draft state and coordinates the four Passdown tabs and PDF companion. `PriceEditorViewModel` owns the anchored price edit lifecycle; `EarlyRideTimeEditorViewModel` (Phase 36C, exposed as `AssociateViewModel.EarlyRideTimeEditor`) owns only the compact Early Ride Time panel — its fields, REL-004 save hashes and the five commands — saving through `IErtConfigurationService`, reading the workspace's one `SelectedDate` through a callback and never touching the draft or autosave. View models marshal background notifications through `IUiDispatcher` (`AvaloniaUiDispatcher` in the app) rather than calling `Dispatcher.UIThread` directly. Phase 35 introduced shared tokens/styles, collapsible sidebar, appearance/motion controllers, native navy Windows 11 title bar with high-contrast fallback, compact operating-date selector, Calendar marker styling and list/detail Notes/History and Settings. The Dashboard follows the approved Admissions Overview (Phase 35E-3, `2ec6261`): gate card, passdown, shows, today's dated pricing, operational notes, cached Pass Perks and Official Data; `DashboardView` code-behind switches the gate grid and columns by width (layout only). Phase 37C added the Weather card (approved D4 mock-up) as the first card of the right-hand column (after Shows and before Pricing when stacked): `DashboardWeatherViewModel` (one instance, owned by `OperationsDashboardViewModel.Weather`) observes the shared `IWeatherMonitor` through `IUiDispatcher` with one coalesced rebuild, builds `DashboardWeatherPresentation` from the snapshot, today's park hours and the time, keeps expansion in memory, and offers Refresh Weather only in the expanded details; showing, navigating to or expanding the card never requests weather. Phase 37F: `AssociateViewModel` (optional `IWeatherMonitor`, composed by DI) reads only `IWeatherMonitor.Current` when it captures a PDF request or runs Create PDF, through `Presentation/PassdownWeatherOutlookSource`; it never subscribes, refreshes or starts the monitor, and `PassdownPdfRequest`/`PassdownPdfDocument` carry the captured `PdfWeatherOutlook`. A weather change alone does not schedule a preview refresh; the next refresh, Print or Save PDF regenerates when the outlook differs. Phase 37F follow-up: `AssociateViewModel.IncludeWeatherOutlook` (a check item "Include Weather Outlook" in the Passdown Actions menu after the PDF style choices, two-way bound) is a device preference loaded from `IPassdownWeatherOutlookPreferenceStore` before the first date loads; until it is known, preview captures report Waiting and Create PDF awaits it. Changing it calls `Preview.NotifyContentChanged()` (leading-edge refresh) and saves the preference; when it is off the capture returns no outlook without reading the monitor. Weather appears nowhere else in Desktop (enforced by `WeatherActivationGuardTests`). Phase 35G removed the unused Phase 23B `ShowColumnsPanel` and the retired Fury 325 banner asset; tests assert they stay retired. Visual review uses `tools/visual-fixtures` (one scenario per process; headless renders are not Windows evidence). Preserve keyboard access, local-only presentation actions and latest-edit/date safety.
